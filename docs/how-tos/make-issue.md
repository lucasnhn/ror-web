# How to - make issue

## General good practices

- An issue should be relatively small. Each issue should end in a PR, and no one wants to review a PR that is too large.
- If an issue becomes too large, or starts including more functionality than originally thought, I prefer making new issues over sub issues. A sub issue will have a PR that is performed against its parent issue, and not main. Therefore, when the parent issue has a PR towards main, the code in the sub issues will be reviewed twice.
- Of course, it is not always possible to perform smaller tasks in separate issues, as they might depend on code in the current issue. Then it is fair to create a sub issue.

### Labels

#### dependancies

#### documentation

Improvements or additions to documentation

#### duplicate

This issue or pull request already exists

#### enhancement

New feature or request

#### good first issue

Good for newcomers

#### help wanted

Extra attention is needed

#### invalid

This doesn't seem right

#### javascript

#### question

Further information is requested

#### third-party

Issue relates to third-party packages

#### wontfix

This will not be worked on

### Type

Select type that is most describing to what you will do.

#### Bug

An unexpected problem or behaviour

#### Feature

A request, idea or new functionality

#### Task

A specific piece of work (usually used whenever bug and feature isn't relevant)
